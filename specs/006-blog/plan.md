# Implementation Plan: Blog Page

**Branch**: `006-blog` | **Date**: 2025-12-26 | **Spec**: `/specs/006-blog/spec.md`
**Input**: Feature specification from `/specs/006-blog/spec.md`

## Summary

Implement a blog section for the Physical AI & Humanoid Robotics course documentation site to publish course announcements, technical tutorials, and module updates. The blog will leverage Docusaurus 3.9.2's built-in blog plugin to provide chronological post listings, tag-based filtering by module (ROS2, Gazebo, Isaac, VLA), and call-to-action links from blog posts to related course modules. All blog posts will be markdown files with frontmatter metadata (title, date, author, tags) stored in `frontend-book/blog/`, integrated with the existing purple+black UI theme.

**Technical Approach**: Enable Docusaurus blog plugin (already included in classic preset), create blog post markdown template with frontmatter schema, configure blog settings in `docusaurus.config.ts`, create reusable ModuleCTA component for linking blog posts to course modules, and extend purple+black CSS theme to blog pages. Blog posts will auto-generate RSS feed, tag pages, and pagination without custom logic.

## Phase 1: Design & Entity Definitions

**Purpose**: Define blog post frontmatter schema, author metadata structure, and ModuleCTA component API.

### Outputs

#### 1. `data-model.md` - Entity Definitions

**Entities**:

1. **BlogPost** (markdown file)
   - Frontmatter properties:
     - `title`: string (required) - Post headline
     - `date`: ISO 8601 date (required) - Publish date
     - `authors`: string | string[] (optional) - Author(s) key(s) from authors.yml
     - `tags`: string[] (required) - Module tags (e.g., ["ROS2", "tutorial"])
     - `description`: string (optional) - Custom excerpt (150-200 chars)
     - `image`: string (optional) - Featured image path
     - `slug`: string (optional) - Custom URL slug
   - Content: Markdown body with MDX support

2. **Author** (authors.yml entry)
   - `name`: string - Full name
   - `title`: string (optional) - Role/title
   - `url`: string (optional) - Personal website or GitHub
   - `image_url`: string (optional) - Avatar URL

3. **Tag** (auto-generated by Docusaurus)
   - `label`: string - Display name (e.g., "ROS2")
   - `permalink`: string - Tag page URL (e.g., "/blog/tags/ros-2")
   - `count`: number - Number of posts with this tag

4. **ModuleCTA** (React component)
   - Props:
     - `moduleName`: "ROS2" | "Gazebo" | "Isaac" | "VLA"
     - `moduleNumber`: 1 | 2 | 3 | 4
     - `moduleTitle`: string - Full module name
     - `moduleUrl`: string - Link to module landing page

#### 2. `quickstart.md` - 5-Step Implementation Guide

**Step 1**: Enable Docusaurus Blog Plugin (verify configuration)
**Step 2**: Create Author Metadata (`blog/authors.yml`)
**Step 3**: Create First Blog Post (`blog/2025-12-26-welcome.md`)
**Step 4**: Create ModuleCTA Component (`src/components/ModuleCTA/`)

## Phase 2: Architecture Decisions

### Decision 1: Blog Plugin vs Custom Blog Implementation

**Context**: Docusaurus provides built-in blog plugin vs building custom blog from scratch

**Options**:
1. Use Docusaurus blog plugin (recommended)
2. Build custom blog with manual routing and pagination

**Decision**: Use Docusaurus blog plugin

**Rationale**:
- Already included in `@docusaurus/preset-classic`
- Auto-generates tag pages, RSS feed, pagination
- Zero additional dependencies
- Well-documented and maintained
- Reduces implementation complexity by 80%

**Trade-offs**:
- Less customization flexibility (constrained to Docusaurus conventions)
- Cannot change URL structure significantly
- Tag filtering is page-based (not dynamic filtering on same page)

**Consequences**:
- Fast implementation (1-2 days vs 1-2 weeks for custom)
- Automatic upgrades with Docusaurus version updates
- Must follow Docusaurus blog frontmatter schema

---

### Decision 2: Tag Naming Convention

**Context**: Module tags need consistent naming across blog posts and module pages

**Options**:
1. Use technical names: `ros2`, `gazebo`, `isaac`, `vla`
2. Use display names: `ROS2`, `Gazebo`, `Isaac Sim`, `VLA`
3. Use descriptive names: `Module 1 - ROS 2`, `Module 2 - Gazebo`

**Decision**: Use display names (Option 2) with URL-safe slugs

**Rationale**:
- Display names are user-friendly and recognizable
- Docusaurus auto-converts tags to URL-safe slugs (e.g., "ROS2" → "ros-2")
- Consistent with module naming in main site navigation
- No need for tag mapping or translation layer

**Trade-offs**:
- Slightly longer tag labels in UI
- Must ensure consistent capitalization across all posts

**Consequences**:
- Tag labels: `ROS2`, `Gazebo`, `Isaac`, `VLA`, `Tutorial`, `Announcement`
- Tag URLs: `/blog/tags/ros-2`, `/blog/tags/gazebo`, `/blog/tags/isaac`, `/blog/tags/vla`
- Authors must use exact tag names (case-sensitive)

---

### Decision 3: ModuleCTA Component Placement

**Context**: Blog posts need to link to related course modules with clear CTAs

**Options**:
1. Inline CTA within markdown content (manual placement by author)
2. Automatic CTA at bottom of every tagged post (generated from frontmatter)
3. Sidebar CTA component (separate from main content)

**Decision**: Automatic CTA at bottom of tagged posts (Option 2)

**Rationale**:
- Consistent placement across all blog posts
- Auto-generated from `tags` frontmatter (no manual work per post)
- Always visible without breaking content flow
- Easier to maintain and update module URLs centrally

**Trade-offs**:
- Less flexible positioning (always at bottom)
- Cannot customize CTA text per post

**Consequences**:
- Create `BlogPostModuleCTA` component that renders after blog content
- Component reads `tags` from frontmatter and maps to module URLs
- Module mapping stored in component file (easy to update)

---

### Decision 4: Blog Post URL Structure

**Context**: Docusaurus supports multiple URL formats for blog posts

**Options**:
1. Date-based: `/blog/YYYY/MM/DD/post-title` (default)
2. Title-only: `/blog/post-title` (via `routeBasePath` config)
3. Custom slugs: `/blog/custom-slug` (via `slug` frontmatter)

**Decision**: Use default date-based URLs (Option 1) with custom slug support

**Rationale**:
- Date-based URLs provide chronological context
- SEO-friendly and human-readable
- Custom slugs available for special posts (e.g., `/blog/getting-started`)
- Aligns with industry standard blog practices

**Trade-offs**:
- Longer URLs than title-only approach
- Date is visible in URL (may feel dated for evergreen content)

**Consequences**:
- Default URL format: `/blog/2025/12/26/welcome-to-physical-ai`
- Custom slugs override date path when specified in frontmatter
- No configuration changes needed (use Docusaurus defaults)

---

### Decision 5: Author Metadata Storage

**Context**: Blog posts need author information (name, avatar, bio)

**Options**:
1. Inline author data in each post's frontmatter
2. Centralized `authors.yml` file (Docusaurus convention)
3. External author API or database

**Decision**: Use centralized `blog/authors.yml` file (Option 2)

**Rationale**:
- Single source of truth for author data
- Easy to update author bio/avatar across all posts
- Docusaurus natively supports authors.yml
- No API dependencies or build-time data fetching

**Trade-offs**:
- Must create authors.yml before first blog post
- Author keys must match across all posts (risk of typos)

**Consequences**:
- Create `blog/authors.yml` with default author entry
- Blog post frontmatter references author by key: `authors: [default]`
- Can add multiple authors per post: `authors: [alice, bob]`

---

### Decision 6: Purple+Black Theme Extension

**Context**: Blog pages must match existing purple+black UI theme

**Options**:
1. Create separate `blog.css` file with blog-specific styles
2. Extend existing `custom.css` with blog CSS selectors
3. Swizzle Docusaurus blog components and inline styles

**Decision**: Extend existing `custom.css` (Option 2)

**Rationale**:
- Centralized styling in one file
- Blog inherits all existing purple+black CSS variables
- No component swizzling needed (easier to upgrade Docusaurus)
- Minimal code changes

**Trade-offs**:
- `custom.css` file grows larger (acceptable for 20-30 additional lines)
- Blog-specific selectors mixed with global styles

**Consequences**:
- Add blog CSS selectors to `frontend-book/src/css/custom.css`:
  - `.blog-list__item` - Blog post list styling
  - `.blog-post-meta` - Author/date metadata styling
  - `.blog-tags` - Tag list styling
  - `.blog-module-cta` - ModuleCTA component styling

## Risks & Mitigation

**Risk 1**: Docusaurus blog plugin doesn't support required customization
- **Likelihood**: Low (plugin is well-documented and flexible)
- **Impact**: Medium (may need to swizzle components or build custom solution)
- **Mitigation**: Review Docusaurus blog plugin docs in Phase 0 research; test customization options early

**Risk 2**: ModuleCTA component breaks blog layout on mobile
- **Likelihood**: Medium (responsive design complexity)
- **Impact**: Low (visual issue, not functional blocker)
- **Mitigation**: Test ModuleCTA on multiple viewport sizes; use CSS Grid/Flexbox for responsive layout

**Risk 3**: Tag naming inconsistency across blog posts
- **Likelihood**: High (human error when writing posts)
- **Impact**: Low (posts won't appear in tag filters, but still browsable)
- **Mitigation**: Create blog post template with pre-defined tag options; document tag conventions in quickstart guide

**Risk 4**: RSS feed doesn't include full content
- **Likelihood**: Low (Docusaurus auto-generates full RSS)
- **Impact**: Low (users can still visit blog for full posts)
- **Mitigation**: Test RSS feed generation in Phase 7 validation; configure `feedOptions` if needed
